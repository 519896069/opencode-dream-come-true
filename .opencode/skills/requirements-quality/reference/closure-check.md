# 逻辑闭环检查

验证需求逻辑自洽、无矛盾的检查指南。

## 检查维度

### 功能依赖

**检查点：**
- 功能之间的调用关系是否清晰？
- 有没有循环依赖？
- 依赖关系是否合理？
- 每个功能的输入和输出是否明确？

**示例：**
```
用户下单 → 扣减库存 → 生成订单 → 支付
如果支付失败，库存要不要回滚？订单状态怎么变？
```

**检查方法：**
1. 列出所有功能
2. 画出功能依赖图
3. 检查是否有循环依赖
4. 验证每个功能的输入和输出

### 数据流

**检查点：**
- 数据从哪来？
- 数据到哪去？
- 中间经过哪些转换？
- 每一步的数据格式是否一致？

**示例：**
```
用户输入 → 前端校验 → 后端校验 → 数据库存储 → 返回结果
如果某一步失败，数据怎么回滚？用户怎么知道？
```

**检查方法：**
1. 从数据源头开始
2. 追踪数据的每一步转换
3. 验证数据的最终去向
4. 检查每一步的数据格式

### 状态转换

**检查点：**
- 状态定义是否清晰？
- 状态转换条件是否明确？
- 有没有死锁状态？
- 每个状态的后续状态是否明确？

**示例：**
```
订单状态：待支付 → 已支付 → 已发货 → 已完成
如果退款，状态怎么变？库存怎么恢复？
```

**检查方法：**
1. 列出所有状态
2. 标注状态转换条件
3. 检查是否有死锁状态
4. 验证每个状态的后续状态

### 业务规则

**检查点：**
- 规则是否矛盾？
- 规则是否一致？
- 规则是否完整？
- 规则是否有歧义？

**示例：**
```
规则1：用户只能修改自己的订单
规则2：管理员可以修改所有订单
问题：管理员修改订单时，是否算作"用户的订单"？
```

**检查方法：**
1. 列出所有业务规则
2. 检查规则是否矛盾
3. 检查规则是否一致
4. 检查规则是否完整

### 边界条件

**检查点：**
- 正常流程是否覆盖？
- 异常流程是否覆盖？
- 边界值是否考虑？
- 极端情况是否处理？

**示例：**
```
正常流程：用户提交订单
异常流程：库存不足、支付失败、网络超时
边界值：最大订单金额、最小订单金额、最大商品数量
极端情况：并发提交、重复提交、恶意提交
```

**检查方法：**
1. 列出所有正常流程
2. 列出所有异常流程
3. 列出所有边界值
4. 列出所有极端情况

## 检查方法

### 画依赖图

**步骤：**
1. 列出所有功能模块
2. 标注每个功能的输入和输出
3. 画出功能之间的调用关系
4. 检查是否有循环依赖

**输出格式：**
```
┌─────────────┐     ┌─────────────┐
│   功能A     │────▶│   功能B     │
└─────────────┘     └─────────────┘
       │                    │
       ▼                    ▼
┌─────────────┐     ┌─────────────┐
│   功能C     │◀────│   功能D     │
└─────────────┘     └─────────────┘
```

### 追踪数据流

**步骤：**
1. 从数据源头开始（用户输入/数据库/外部接口）
2. 追踪数据的每一步转换
3. 验证数据的最终去向（存储/返回/展示）
4. 检查每一步的数据格式

**输出格式：**
```
数据源 → 格式校验 → 业务处理 → 数据存储 → 结果返回
         │           │           │           │
         ▼           ▼           ▼           ▼
       校验失败    处理失败    存储失败    返回失败
       → 错误提示   → 回滚      → 重试      → 降级
```

### 验证状态转换

**步骤：**
1. 列出所有状态
2. 标注每个状态的转换条件
3. 画出状态转换图
4. 检查是否有死锁状态

**输出格式：**
```
[初始状态] ──条件1──▶ [状态A] ──条件2──▶ [状态B]
                            │
                           条件3
                            │
                            ▼
                        [终态]
```

### 检查规则一致性

**步骤：**
1. 列出所有业务规则
2. 检查规则是否矛盾
3. 检查规则是否一致
4. 检查规则是否完整

**输出格式：**
| 规则编号 | 规则内容 | 冲突规则 | 冲突类型 |
|----------|----------|----------|----------|
| R001 | 用户只能修改自己的订单 | R002 | 权限冲突 |
| R002 | 管理员可以修改所有订单 | R001 | 权限冲突 |

## 闭环标准

当以下条件都满足时，逻辑闭环验证通过：

1. **功能依赖清晰**
   - 每个功能都有明确的输入和输出
   - 没有循环依赖
   - 依赖关系合理

2. **数据流完整**
   - 每个数据都有明确的来源和去向
   - 每一步的数据格式一致
   - 失败时有回滚或降级方案

3. **状态转换自洽**
   - 每个状态都有明确的转换条件
   - 没有死锁状态
   - 每个状态的后续状态明确

4. **业务规则一致**
   - 规则没有矛盾
   - 规则没有歧义
   - 规则覆盖所有场景

5. **边界条件覆盖**
   - 正常流程覆盖
   - 异常流程覆盖
   - 边界值考虑
   - 极端情况处理
