# M2: 任务拆分

**需要用户确认：** ✓

**产物：** tasks.md, tasks/*.md

## 执行流程

1. **调用代码规范 skill**
   ````
   skill({ name: "standards" })
   ````

2. **读取设计文档**
   - 读取 checkpoint.md（功能概述、验收条件）
   - 读取 user-store.md（用户故事、操作流程）
   - 读取 design.md（数据库、后端、前端设计）
   - 读取 api.json（API 接口定义）
   - 如果存在 brief.md，读取前端设计 brief

3. **识别交叉定义**
   - 分析 dto、entity、model 等交叉定义
   - 为交叉定义生成前置任务（P0 优先级）

4. **拆分任务**
   - **红线规则：任务拆分必须遵循 design.md 中的路由/页面定义**
     - 同一个路由/页面的任务必须在同一个 Task 中完成
     - 禁止将一个需求拆分到多个页面
     - 如果 design.md 指定在现有页面中修改，任务必须指定现有页面路径
   - 每个接口/组件/函数拆为一个 Task
   - 分析依赖关系
   - 确定执行顺序
   - **判断任务类型**：
     - 如果是前端页面修改/新增任务，在工作内容中加入 skill 调用指示
     - 只有前端任务才会出现这个描述，其他项目没有
     - 如果存在 brief.md：`skill({ name: "impeccable" }) <brief.md地址>`
   - **前端任务必须明确**：
     - 所属路由路径（如 /admin/sms/mobile-rule）
     - 所属页面文件（如 src/views/sms/MobileRule.vue）
     - 是否在现有页面中修改（禁止擅自新建页面）

5. **搭建开发环境（可选）**
   - 先询问用户：是否已有 worktree 目录？
     - 如果已有：询问用户 worktree 路径，直接使用该路径
     - 如果没有：调用 `skill({ name: "git-workspace-setup" })` 创建
       - skill 参数：
         - `<design_path>`：design.md 文件路径（从上下文获取）
         - `<base_branch>`：基分支名称（从上下文获取或询问用户）
         - `<iteration>`：迭代名称（从上下文获取或询问用户）
         - `<feature>`：需求名称，英文（从上下文获取或询问用户）
         - `<developer>`：开发者姓名缩写，默认 `fzp`
         - `<workspace_root>`：当前工作目录（从上下文获取）
   - 记录 worktree 路径，后续任务文件的工作目录基于此路径

6. **生成 tasks.md（任务路由文件）**
   - 任务依赖关系图（使用 Mermaid 或文本格式）
   - 执行顺序（明确分轮次，标注哪些任务可以并发执行）
   - 任务文件映射表（任务ID → 任务文件路径）
   - 上线标准

7. **生成 tasks/ 目录下的独立任务文件**
   - 为每个任务生成独立文件：tasks/T-001.md, tasks/T-002.md, ...
   - 每个任务文件包含以下字段：

     ```markdown
     # {任务ID}: {任务名称}

     ## 工作目录
     <workspace_root>/worktree/<branch_name>/<project_name>/
     - 其中 <project_name> 从 design.md 的"涉及项目"中提取（取路径最后一级目录名）
     - 示例：worktree/dev_v1/feature_xxx_fzp/console-api/

     ## 代码目录
     {具体修改的代码目录，如 src/handler/、src/model/}

     ## 任务依赖
     - {依赖任务ID}：{依赖任务名称}

     ## 工作内容
     - 生成 {文件1}
     - 实现 {函数1}

     ## 详细逻辑设计
     1. {步骤1}
     2. {步骤2}

     ## 边界情况处理
     | 场景 | 处理方式 |
     |------|----------|
     | {场景1} | {处理方式1} |

     ## 函数链路图
     Controller → Service → Model → MySQL

     ## 真实单元测试代码
     - 生成测试代码前，**必须调用** `skill({ name: "unit-test-quality" })` 获取测试规范
     - 根据项目类型，**必须读取**对应示例文件：
       - Go 项目：`reference/go-examples.md`
       - 前端项目：`reference/frontend-examples.md`
     - 测试必须验证函数行为，禁止 `a = a` 的无意义断言
     - 测试必须 Mock 外部依赖
     - 测试必须覆盖：正常流程、错误处理、边界条件
     - 每个测试必须调用被测函数并验证返回值或副作用

     ## 风险评估
     - 影响范围: {影响范围}
     - 风险等级: {低/中/高}

     ## 审查要点
     - [ ] {审查点1}

     ## 验收标准
     - [ ] {验收点1}

     ## 执行要求
     1. 先 cd 到工作目录执行任务
     2. 执行编码任务，生成/修改代码
     3. 调用 dct_validate 验证产物，必须传递 workDir 参数：
        dct_validate(taskId: "{任务ID}", artifact: "{产物路径}", workDir: "{工作目录}")
     4. 如果验证失败，根据错误信息修改代码，重新验证，最多重试 3 次
     5. 执行完成后，返回以下 JSON 格式：
        {
          "taskId": "{任务ID}",
          "status": "success | failed",
          "artifacts": ["{产物路径1}", "{产物路径2}"],
          "message": "任务完成",
          "errors": [],
          "retryCount": 0
        }
     ```

8. **单元测试要求**
   - 生成测试代码前，先调用 `skill({ name: "unit-test-quality" })` 获取测试规范
   - 测试必须验证函数行为，禁止 `a = a` 的无意义断言
   - 测试必须 Mock 外部依赖（数据库、外部服务）
   - 测试必须覆盖：正常流程、错误处理、边界条件
   - 每个测试必须调用被测函数并验证返回值或副作用

9. **验证产物**
   - 调用 dct_validate 验证 tasks.md

10. **用户确认**
    - 询问用户是否通过
    - 如果不通过，根据反馈修改产物

11. **更新看板状态**
    - 修改 kanban.md，将 M2 标记为已完成
    - 将编码任务添加到看板，每个任务卡片格式：
      - [ ] T-001: {任务名称} [file: tasks/T-001.md]
